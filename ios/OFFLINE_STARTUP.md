# Birzzle Fever 1.0.4: iOS 6 startup network gate

## Evidence and patch scope

The operator observed a network error at the splash screen on iPad2,1 / iOS 6.1.3. The game process emitted three network-initialization errors; the captured logs contain **no game request URL, HTTP status, or server reply**, and no native crash report was copied. See `findings/first-launch-network-error.json`. The error message's literal is not in the app executable, so those log lines alone do not establish which app branch failed. The exact dialog wording was not recorded.

Static analysis of the clean IPA (SHA-256 `544b0eec4836ab906733c36090b8d736face61dc25723ed7a127949f432ef053`) resolves two native paths using the bundled host `gs-birzzlefeverhb.enfeelcdn.com`. Host setup at image addresses `0x17f7e0` and `0x22ef88` calls a shared TCP connectivity probe at `0x1fad08`. That probe uses `socket`, `inet_pton`, `connect`, `select`, and `getsockopt`, and returns a boolean. Two asynchronously scheduled `NETWORKCHECK` paths invoke the host check. The two `BL 0x1fad08` callsites are at `0x17f830` and `0x22efd8`; these addresses are relative to the Mach-O image, not an ASLR-adjusted process address. Their file offsets are `0x17b830` and `0x22afd8` because `__TEXT` begins at file offset zero and VM address `0x4000`.

`patch_startup_probe.py` replaces **only** those two calls with Thumb `movs r0, #1; nop`, leaving the host setup, callbacks, subsequent server requests, and application data alone. A positive TCP probe does **not** replace a server response. This is a targeted gate experiment, **not a claim of playable offline mode**. In particular, the executable also compares command strings `SERVER.INIT` and `POCKET.LOGIN` in a native service dispatch function at `0x1c6b48`; its request/response schema and the first live failure are not identified. `ConnectorProxy` has native `requestComplete:handle:response:` (`0x1d6038`) and `requestFail:handle:message:` (`0x1d60c8`) methods which both route to `0x206c60`; synthetic success without a proven response payload could corrupt in-game state and is deliberately absent.

## Deployment, data safety, and rollback

**Do not uninstall the installed game to try this patch:** uninstalling can remove its Documents/Library save data. Do not deploy until the installed app's container and original executable have been backed up and a jailbreak-compatible code-signing/update path is known. Patching the Mach-O invalidates its original code signature; the Python builder does not sign the IPA, install it, or modify the device. The untouched clean IPA is the rollback source for the executable, but restoring by uninstall/reinstall is unsafe without a verified container backup. Existing MobileSubstrate dylibs in the captured process have an unknown effect on the splash failure.

The host's `ideviceinstaller -g/--upgrade` completed an in-place update; `-U/--uninstall` was never used. The unmodified full-app backup under ignored `ios/captures/backup-20260926T044656Z/` passed ZIP integrity checks and contains Documents, Library, and the executable matching the clean IPA. A post-upgrade archive under `ios/captures/post-upgrade-20260926T044903Z/` confirms the installed executable matches the intended two-call patch; other app-bundle member contents are unchanged. All 12 container files remain present; 11 are byte-identical, while a Documents SQLite analytics table gained three records. Save contents were not published.

When the operator explicitly starts a **new** manual test, first use the repository's pre-flight notification and readiness gate; then launch an app-focused log capture *before* manually opening the updated game. Observe whether the splash progresses, the network alert changes, or a specific `SERVER.INIT` / `POCKET.LOGIN` request fails. Do not repeat the previous run merely to reconfirm the already reported error. If a backend exchange remains required, map the actual request and response format before implementing a local response; do not feed Android cache bytes to this iOS build on assumption.

## Static startup service and success-path boundary

The first-party `ConnectorProxy config:` method at image address `0x1d5e44` copies an `NSString`'s UTF-8 bytes into a runtime server buffer at `0x4936e0` (`__bss`, **not** the archive's on-disk bytes). Its C++ caller at `0x205cd0` takes a runtime C-string prefix. Three observed native callers pass the archive's default `http://gs-birzzlefeverhb.enfeelcdn.com`; two others pass runtime strings. `ConnectorProxy request:handler:api:params:` at `0x1d5e70` passes that buffer to `RankingCore` along with the numeric request ID and caller-supplied API/parameters. This identifies a **default configured host**, not proof that request ID 1 used that host after runtime configuration. No full URL, query or device-specific value needs to be logged to preserve this distinction.

The successful path is different from the observed failure: `RankingCore -connectionDidFinishLoading:` at `0x1d55c8` converts received bytes to a string with `initWithData:encoding:` and calls `ConnectorProxy requestComplete:handle:response:` at `0x1d6038`; the C++ receiver at `0x206c60` uses `runDecrypt:` and a parser exposing `objectWithUTF8String:length:`. The archive establishes a decrypt/parse/dispatch flow, **not** the keys, identity data, state transitions or output shape expected for the first request. No successful iOS startup response was captured. Until request ID 1's effective host and reply contract are known, a made-up JSON payload or bypass of DNS failure would be misleading and could corrupt game state.

## Private historical conversion and guarded startup experiment — operator-tested

`prepare_offline_history.py` reads the **original** Android backup and the hash-checked clean iOS IPA without modifying either. It authenticates CCrypt2 records, checks timestamps and decrypts all 13 historical JSON replies, then assembles the **separate inbound iOS wire format**: `base64(AES-ECB(MD5(json) + json + PKCS#7, iOS incoming key))`. The incoming key is reconstructed from the original `runDecrypt:` tables; its value, account fields and response bodies are never printed. A build-time decoder independently checks all 13 replies against their original JSON. The JSON `commandid` is a **numeric request ID**, not the symbolic API; the historical `SERVER.INIT` ID equals observed iOS ID 1, but later historical IDs cannot safely be replayed against arbitrary iOS counters. The original `stage.dat` is authenticated but has malformed content and no `DATA` field; it is **not** offered as a usable Keychain save. Seven other authenticated static save records are prepared in an ignored, private artifact; **none has been installed into the iPad Keychain**.

This experiment does not replace a server or log identifiers, but still waits for the underlying connection failure before delivering the local startup reply; it is **not playable offline** and does **not** populate Keychain or migrate the historical UID. ## Original iOS callback crash root cause and staged compatibility fix

Static traceback of the accepted startup result identified a **specific cross-platform incompatibility**, not merely an unknown Keychain or worker fault. In the authenticated historical Android `SERVER.INIT` reply, `timeout` is the string representing integer one. The iOS consumer at image VM `0x180d44` reads that field, converts it to an integer at `0x180d60`, and passes it to `0x1822c8`. A nonzero value there is copied into an async worker block's pointer slot (`0x182346`); the block's cleanup function is exactly `0x1c83b1` (computed by the original PC-relative callback reference at `0x18232c`). On the crashed worker, that callback called a C++ map lookup with pointer `0x1`, faulting at `0x1cfcf4`, matching the incident's `KERN_INVALID_ADDRESS at 0x1`. The original iOS `0x1822d2` zero branch avoids scheduling this invalid-pointer cleanup. This establishes **why replaying the unmodified Android timeout crashed the iOS code**; it does not imply all later game requests are compatible.

The first local-only `ios/BirzzleFever-HB-offline-startup-ios-timeout.ipa` adapted just the startup reply and was **never installed**. The builder creates a distinct `ios/BirzzleFever-HB-offline-two-replies-ios-timeout.ipa`, re-authenticating both cached responses and setting each inbound iOS `timeout` to the original iOS no-remote-timeout branch. For `SERVER.INIT` only, it also changes `requestversion` to the original iOS binary's unique `2.0.17.HBI` literal.
